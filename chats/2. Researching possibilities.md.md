## Audio capture

### 1. Device selection
You list the devices, resolve the user's choice and check that they work before loading any model.

| Option | Pros | Cons |
|---|---|---|
| Choose by index | Simple and exact | Indexes change when headsets are plugged in or removed |
| Choose by name substring | Survives re-plugging; easy to type | Can match more than one device, so it must fail if the match is ambiguous |
| Default devices (no flags) | Nothing to type | Wrong at an interview if Windows switched the default to a different headset |

Suggestion: allow both a name and an index, and print which device was resolved at startup. That makes risk #6 visible straight away.

### 2. Stream capture
You open the mic as an input stream and the output device as a **WASAPI loopback** stream at the same time.

| Library | Pros | Cons |
|---|---|---|
| `PyAudioWPatch` (PortAudio fork) | Real WASAPI loopback; callback API; one library for both sources | Windows-only fork with a smaller community; API is in the PyAudio style |
| `soundcard` | Very simple; loopback through `include_loopback=True` | Blocking `record()` calls, so you write the threading yourself; less control over buffer sizes; maintained less actively |
| `sounddevice` | Clean, well-maintained API; good for the mic | Standard PortAudio has no WASAPI loopback, so you'd still need a second library for system audio |
| Virtual cable (VB-Cable) | Works with any library | Excluded by your plan; changes the user's audio routing |
| Raw WASAPI via `comtypes` | Full control | Many hours of COM code, which doesn't fit a 20 h budget |

You also decide how audio is read:
- **Callback mode** runs on the audio thread and has the lowest jitter. It must do almost nothing beyond copying the chunk into a queue.
- **Blocking reads** in your own thread are easier to reason about. If the thread falls behind, you risk overflow.

**Chunk size** is a trade-off. Around 10 ms gives lower latency but more Python overhead. Around 30 ms costs less CPU and adds negligible delay against a 5 s budget. Chunks of about 32 ms match Silero's frame size well.

**Gotcha:** a WASAPI loopback stream delivers **no packets while nothing is playing**. It does not send zeros. Code that expects a steady stream will stall, and timestamps based on sample counts will drift. Plan for gaps from the start.

### 3. Normalize format
Windows shared mode hands you the device mix format, usually 48 kHz stereo float. That differs per device, and ASR needs 16 kHz mono.

| Step | Options | Trade-off |
|---|---|---|
| Downmix | Average the channels vs. take one channel | Averaging is safe. Taking one channel risks silence on oddly wired devices |
| Resample | `soxr` (streaming), `scipy.signal.resample_poly`, `torchaudio` | `soxr` is fast, high quality and **stateful across chunks**. Resampling each chunk on its own with `resample_poly` leaves clicks at chunk edges. `torchaudio` adds a heavy dependency for little gain |
| Sample type | float32 in [-1, 1] vs int16 | float32 is what Silero and Whisper expect. int16 saves memory, which doesn't matter here |

### 4. Timestamp and queue
Each chunk gets a time on one session clock. It is then passed on without the capture thread ever waiting.

| Clock option | Pros | Cons |
|---|---|---|
| `time.monotonic()` stamped in the callback | Simple; the two sources line up on one clock; works across loopback gaps | Includes driver buffering jitter (tens of ms, irrelevant at 1 s display precision) |
| Sample counting from stream start | Precise within one stream | Breaks during loopback silence gaps; mic and output device clocks drift apart |

| Handoff option | Pros | Cons |
|---|---|---|
| Unbounded `queue.Queue` | Simplest; never blocks | Memory and delay can grow without limit (risk #8) |
| Bounded queue with drop-oldest | Delay has a ceiling | Can lose audio under extreme load, which should be logged by metrics |
| NumPy ring buffer | No per-chunk allocation | More code, and no benefit at this data rate |

The raw-audio queue can stay small and simple because VAD is cheap. The bounded, policy-controlled queue belongs *after* segmentation, where the models are.

## ASR

### 5. Voice activity detection (segmentation)
This turns the continuous stream into phrases. **This step decides most of your latency**: the 5 s clock starts when the phrase ends, so pause detection is pure waiting time.

| Option | Pros | Cons |
|---|---|---|
| Silero VAD | Accurate on noisy and compressed call audio; about 1 ms per 32 ms frame on CPU; ONNX or torch | Small torch/onnxruntime dependency |
| WebRTC VAD | Extremely fast and tiny | More false triggers on noise and music; coarse aggressiveness levels |
| Energy threshold | No dependency | Breaks with background noise and varying call volume |
| pyannote segmentation | Also detects speaker changes | Heavy; overkill for this step |
| faster-whisper's built-in `vad_filter` | Free if you use faster-whisper | Works on finished audio, not live streams, so it can't drive segmentation |

The tunable parameters each pull in opposite directions:
- **Minimum silence to end a phrase (~400–700 ms):** shorter gives faster output but cuts sentences mid-thought, which hurts ASR and translation.
- **Maximum segment length (~8–15 s):** shorter bounds latency on monologues, but cuts land mid-word.
- **Minimum speech length (~250 ms):** drops coughs and clicks, which Whisper tends to hallucinate on.
- **Speech padding (~100–200 ms):** keeps word onsets, but adds a little silence back in.

### 6. Feature extraction
The waveform becomes a log-mel spectrogram: 80 bins for older Whisper models, 128 for large-v3 and turbo. This is usually done **inside the ASR library**, so in practice the choice is made by step 7.

The one real decision is **padding**. Whisper always processes a 30 s window, so a 2 s phrase costs about as much encoder compute as a 30 s one. faster-whisper handles this efficiently. Some fine-tunes in `transformers` let you trim the window, but that can reduce accuracy. Optional denoising (e.g. `noisereduce`) is generally **not** worth it: Whisper is trained on noisy audio, and denoising adds latency and artifacts.

### 7. Model inference
There are two independent choices: **runtime** and **model**.

| Runtime | Pros | Cons |
|---|---|---|
| `faster-whisper` (CTranslate2) | Several times faster than reference Whisper; fp16/int8; low VRAM; mature | Fine-tunes need converting with `ct2-transformers-converter` |
| HF `transformers` | Runs every model directly (Whisper fine-tunes, MMS, Seamless) | Slower and uses more memory for the same model |
| `whisper.cpp` | Strong CPU performance, a good fallback | Python bindings are less mature; a second toolchain to maintain |
| `openai-whisper` | Reference implementation | Slowest; no real advantage |

| Model family | Pros | Cons |
|---|---|---|
| Whisper large-v3 | Best general multilingual accuracy | Slowest; can be tight against a 2 s transcription budget on a laptop GPU |
| Whisper large-v3-turbo | Much faster decoder (4 layers) | Quality loss tends to be larger on low-resource languages, so measure it on Armenian |
| Armenian Whisper fine-tunes | Can beat base models on hy | Quality varies widely; often trained only on read speech (Common Voice); risk of overfitting |
| MMS-1b-all + hy adapter (CTC) | Fast, non-autoregressive, so no looping hallucinations | No punctuation or casing (hurts MT); often weaker on conversational speech |
| SeamlessM4T v2 | Can also translate directly | Large; gives you less control over the separate HY/EN outputs you need |

**Precision:** fp16 on GPU is the default. `int8_float16` halves VRAM, which helps when ASR, MT and the speaker model share one GPU, at a small accuracy cost. CPU int8 is the fallback and will probably only meet the latency limit with smaller models.

**Batching:** if both sides speak at once, you can run the two segments one after another (simple, predictable) or batch them (more throughput, more code). Running them in order is probably enough. Let the metrics decide.

### 8. Decode and filter
This turns model output into trustworthy text.

| Setting | Options | Trade-off |
|---|---|---|
| Language | Fixed `hy` vs auto-detect | Fixed avoids wrong-language and wrong-script output and saves time. Auto-detect is unnecessary, since input is Armenian only |
| Search | Greedy vs beam size 5 | Beam is usually a bit more accurate but slower. Benchmark both |
| Temperature fallback | On vs off | On recovers bad decodes, but can **re-decode several times**, causing latency spikes. Off keeps latency bounded |
| `condition_on_previous_text` | On vs off | On gives context, but one hallucination can spread into the next segments. Off is safer for independent segments |

Post-filters (cheap and essential):
- Drop segments with high `no_speech_prob` and low `avg_logprob`.
- Drop segments with a high `compression_ratio`, which signals repetition loops.
- Drop known hallucination phrases (subtitle credits, "thanks for watching" and similar), tested on silence and noise clips.
- Check the share of Armenian characters (U+0530–U+058F) and reject output in the wrong script.
- Apply Unicode NFC normalization, keeping Armenian punctuation (`։`, `՞`, `,`) intact for MT.
