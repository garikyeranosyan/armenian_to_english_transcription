## Two decisions to make before starting

1. **Where the shared dataclasses live.** The rules allow no extra modules, so each type should live in the module that produces it:

   - `SpeechSegment` in `segmenter.py`.
   - `TranscriptEntry` in `output.py`. If it lived in `pipeline.py` instead, `output` would import `pipeline` while `pipeline` imports `output`, which is a circular import.
2. **The M2 thin slice versus this order.** In a strict dependency order, `pipeline` comes last. M2, though, needs a working mic-to-terminal path before `speakers` (M4) exists. You can still follow the queue: build a first version of `pipeline` in M2 that labels every segment `Me`, then connect the real `speakers` module in M4. **What `config.py` does**
- **Options:** it reads three command-line options: `--list-devices`, `--mic` and `--output`. Each device option takes a device's index, its exact name, or any unique part of its name, ignoring case.
- **Defaults:** if you leave a device out, it uses the Windows default microphone and default output.
- **Loopback:** the output device you pick is turned into its WASAPI loopback device, so `Settings` holds the `mic` and `loopback` devices that `capture.py` will open.
- **WASAPI only:** it lists only WASAPI devices, and loopback devices never appear as microphones.
- **Errors:** an unknown, ambiguous or missing device stops the program with a message that names the fix, such as using the index or running `--list-devices`.
- **Testing:** the PyAudio instance is passed in rather than created inside, so tests can use a fake one and `capture.py` can reuse the same instance.

**Audio library:** I chose **PyAudioWPatch 0.2.12.8**, pinned in `requirements.txt`. It records system audio through WASAPI loopback without a virtual cable, and has Windows wheels for Python 3.10–3.14. python-sounddevice has no high-level loopback support, and SoundCard has known WASAPI bugs, such as garbage when recording a single channel. I checked the device fields and helper methods against its source code.
