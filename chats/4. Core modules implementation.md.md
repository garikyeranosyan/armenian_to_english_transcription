**What the module does**
- `AudioCapture` records one device using its own sample rate and channel count, as WASAPI shared mode requires. The pipeline will create two of them, one for the mic and one for the loopback.
- Each audio callback converts the sound to 16 kHz mono float32 using soxr, puts an `AudioFrame` (source, start time, samples) on a `queue.SimpleQueue` and returns. It never waits for the code reading the queue.
- `SessionClock` is a single clock that both sources share. Each frame ends at the moment its callback runs, so time stays correct after loopback silence gaps.
- `CaptureError` names the device that failed. Buffer overflows are logged as warnings.

These are the design decisions in `capture.py`. The first four you chose; the rest I made myself without asking, so please check them.

**Your choices**
1. **Where the data types live:** `AudioFrame` and `Source` are defined in `capture.py`.
2. **Resampler:** soxr's streaming resampler, which carries its state from one chunk to the next.
3. **Clock:** wall-clock time read in each callback, from one `SessionClock` shared by both sources.
4. **Hand-off:** an unbounded `queue.SimpleQueue` per source. Nothing is dropped, and capture never waits.

**Choices I made without asking**
5. **Common format is 16 kHz, mono, float32.** Whisper, Silero VAD and ECAPA all expect this. It's the most important of these, because every later module depends on it.
6. **Stereo becomes mono by averaging the channels.** The alternative was to keep only the louder channel. Averaging is standard, but it can quiet a voice that is only on one channel.
7. **The device is opened as float32 at its own sample rate and channel count.** WASAPI shared mode only accepts the device's own rate, so converting ourselves is required. Float32 avoids converting from integers ourselves.
8. **Each callback delivers 32 ms of audio.** That is one Silero VAD window at 16 kHz. Smaller means more callbacks per second; larger adds a little latency.
9. **Callback mode instead of a blocking read loop.** PortAudio pushes audio to us on its own thread, so we don't need a reader thread of our own. The cost is that the callback must stay very short.
10. **A frame's start time is calculated from the resampler's output, not its input.** I chose this because the resampler releases audio in uneven bursts. Timestamps can be early by the resampler's hold-back of 14–55 ms.
11. **Empty resampler output is skipped**, so the segmenter never receives zero-length frames.
12. **Buffer overflow is logged as a warning and recording continues.** The alternative was to raise an error and stop. Stopping mid-call seemed worse than losing a few milliseconds of audio.
13. **The caller creates the queue and passes it in.** This lets the pipeline own the queues and lets tests read them directly.
14. **A device that fails to open raises `CaptureError` with the device's name.** It doesn't retry or fall back to another device.

The ones most worth a second look are **5** (the format), **8** (callback size) and **12** (overflow handling). Tell me which ones you'd change, and whether you want any of them recorded in `DECISIONS.md`.

**What the module does**
